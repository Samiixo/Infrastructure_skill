# Infrastructure Setup v2.0

Протокол закладки фундамента продукта. Цена ошибки здесь - недели или месяцы
переделок, поэтому протокол требует не "выбрать стек", а **выписать
обоснование, отклонённые альтернативы и порог миграции для каждой
сложности**.

Главное отличие v2 от v1: результат **проверяется машинно**. v1 был один
промт на 400 строк, и агент мог отчитаться словами, оставив за кадром
нерешённые решения. Теперь `tools/doctor.py` показывает, что именно не
зафиксировано.

## Когда применять

- Заказчик просит спроектировать архитектуру или выбрать стек.
- Проект стартует с нуля и решение принимается один раз, но живёт годами.
- Агент начал объявлять технологии без сравнения ("возьмём PostgreSQL")
  - это главный симптом, что пора включать протокол.

## Жесткие ограничения (нарушение = FAIL, не WARN)

Это не рекомендации, а constraints. Любое решение по стеку обязано
удовлетворять всем сразу.

1. **Мультиплатформенность** - один бэкенд/API на Web, iOS и Android.
   Бизнес-логика и данные общие, без дублирования и рассинхрона.
2. **Нагрузка** - 1000+ одновременных активных пользователей плюс всплески,
   с документированным путём до 10k и 100k **без смены архитектуры**.
3. **Конкурентность** - корректность при одновременном доступе к одним данным:
   race conditions, конфликты записи, идемпотентность операций.
4. **Безопасность** - OWASP Top 10, осмысленная модель auth, шифрование в
   покое и в движении, секреты не в коде.
5. **Устойчивость к DDoS и злоупотреблениям** - rate limiting, WAF/CDN,
   защита от brute-force, ботов, скрейпинга, abuse API.
6. **Скорость без потери качества** - системные решения с документацией и
   живым community, никакого техдолга "на потом".
7. **Долгосрочная поддерживаемость** - явные слои (данные / логика / API /
   представление), тестируемость, CI/CD с первого дня, инфраструктура как код.
8. **Никаких заглушек в проде** - порядок подключения фич задаётся
   зависимостями, а не удобством.
9. **Юрисдикция данных - только РФ.** Физическое размещение серверов и БД
   только в РФ. Софт при этом любой: self-hosted MongoDB или PostgreSQL в
   российском облаке разрешены, их же зарубежные managed-версии - нет,
   потому что данные покидают РФ независимо от бренда.
10. **Соло-разработчик** - managed предпочтительнее self-hosted, минимум
    разных технологий в стеке, операционная простота важнее теоретической
    правильности.
11. **Порядок: локально -> MVP на РФ-сервере.** Оба окружения описываются с
    самого начала, переход не должен требовать переписывания.
12. **Публичная и авторизованная части - разные слои.** SEO/SSR/SSG для
    публичного, CSR для экранов за логином. Или явное решение, что публичного
    слоя нет.
13. **Не тащить отложенное в работу раньше времени.** Мобильные клиенты,
    не входящие в MVP, фиксируются как deferred с описанием того, что под них
    уже заложено в API и данных.

Подробности и юридическая часть (152-ФЗ, ст. 18 ч. 5, ст. 9, ст. 12,
ст. 18.1, ст. 22, 436-ФЗ, 347-ФЗ, ЗоЗПП) - в `references/constraints.md`.
Юридические утверждения этого скилла проверены по состоянию на 2026-09-02 и
**должны быть перепроверены с юристом** перед использованием: нормы меняются,
а цена ошибки - штрафы.

## Режим работы: gate после каждого этапа

Шесть этапов, каждый закрывается человеческим подтверждением. Не объединять
этапы, не забегать вперёд. Можно упомянуть, что будет на следующем шаге, но
не начинать его.

| Этап | Что делаем | Файл |
|---|---|---|
| 1 | Название и позиционирование | `references/stage1-naming.md` |
| 2 | Выбор стека с обоснованием | `references/stage2-stack.md` |
| 3 | Комплект документации | `references/stage3-docs.md` |
| 4 | Брендбук | `references/stage4-brandbook.md` |
| 5 | HTML/CSS/JS прототип | `references/stage5-prototype.md` |
| 6 | Roadmap API в порядке зависимостей | `references/stage6-roadmap.md` |

Приоритет при конфликте требований: качество и архитектурная корректность
важнее скорости. "Быстрый, но грязный" вариант не предлагается по умолчанию -
только как явно помеченная альтернатива.

## Правило обоснования

Каждый слой стека описывается по одному шаблону:

> **Слой:** [что это]
> **Выбор:** [технология]
> **Почему именно она:** [аргумент, привязанный к constraints выше]
> **Рассмотренные альтернативы:** [минимум 2] - почему отклонены
> **Известные ограничения:** [честно, без приукрашивания]
> **Путь масштабирования:** [что будет при x10 и x100]

И отдельное правило, которое чаще всего нарушают: **любая сложность должна
иметь письменный порог включения.** "Kubernetes" без фразы "переходим при
устойчивой нагрузке от X RPS" - это не решение, а амбиция. Порог пишется
в том же документе, иначе через полгода никто не вспомнит, зачем оно.

## Проверка результата

После того как документация собрана, прогнать аудит покрытия:

    python tools/doctor.py <каталог-проекта>

Выводит по каждой проверке PASS / WARN / FAIL, для FAIL - конкретное
следующее действие. `data_residency` и `pdn_law` - самые дорогие по
последствиям, они падают в первую очередь. Для проекта вне РФ:

    python tools/doctor.py <каталог> --jurisdiction none

Чтобы не выбирать стек наугад, а сравнивать по осям:

    python tools/stack_matrix.py

Матрица не выбирает победителя и не делает вид, что знает ответ. Она даёт
для каждого обязательного слоя кандидатов, решающий вопрос и то, какой
доказательностью вопрос закрывается.

## Чего в протоколе нет намеренно

Код продукта. Прототип из этапа 5 - единственное исключение, и он
принципиально не деплоится. Задача сессии - заложить фундамент, а не начать
стройку: писать код продукта, пока весь план не согласован, запрещено.
