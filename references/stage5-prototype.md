# Этап 5. Прототип на HTML, CSS и JS

Прототип - единственный код, который разрешено писать до согласования плана.
Он существует не для красоты и не для демонстрации навыков, а чтобы заказчик и
разработчик **увидели UX-логику до того, как она будет зашита в бэкенд**.

## Ограничения по конструкции

- **Чистые HTML, CSS и JS.**
- **Без сборки.** Никаких node_modules, бандлеров, транспиляторов и шагов
  "запусти и подожди".
- **Без фреймворков** - ни runtime-фреймворков, ни UI-библиотек.
- **Открывается двойным щелчком** по файлу и сразу показывает суть, без
  локального сервера.

Последний пункт важнее остальных: если для просмотра нужно что-то запустить,
прототип выполнил свою задачу наполовину.

## Что прототип обязан делать

### Видимо следует брендбуку этапа 4

Цвета, шрифты, радиусы, отступы, тон текстов. Это проверяемое требование: если
в прототипе другой синий, чем в палитре, это дефект, а не свобода исполнителя.
Прототип - первая проверка брендбука на практике, а не иллюстрация к нему.

### Демонстрирует 2-4 ключевых экрана или потока

Не все экраны, а самые показательные: то, что является **ядром ценности**
продукта. Если выбрать 10 экранов, ни один не будет показан вдумчиво, и
заказчик не сможет сказать "сюда и сюда" - а это и есть цель этапа.

Выбор экранов: главный путь пользователя от первого входа до получения
ценности плюс один-два момента, которые неочевидны и требуют показа.

### Явно обозначен как прототип-демо

Это требование **визуальное**, а не только в комментарии в коде. В интерфейсе
виден явный признак демо: заголовок или плашка "прототип, данные
искусственные". Молчаливый мок - худший вариант: его потом находят
пользователи.

Данные в прототипе **моковые, и только здесь**. Это не противоречит правилу
"без моков в проде": прототип не деплоится как часть продукта и не является
его кодовой базой. Но прототип не должен ни импортироваться в продакшен, ни
использоваться как источник его данных - и это фиксируется явно.

### Достаточно интерактивен, чтобы дать почувствовать UX-логику

Статичная картинка не проверяет UX. Минимум, который обязан работать:

- **переходы между экранами** по основному сценарию;
- **состояния**: пустое, загрузка, ошибка, заполненное;
- **одна-две формы с валидацией** на стороне клиента;
- **интерактивный элемент, специфичный для продукта**: то, ради чего
  приложение существует.

Не обязательно: настоящий роутинг, модальные окна уровня продакшена, анимации,
адаптив под десять брейкпоинтов.

## Что добавить в 2026

Общий список - в `references/modern-reality.md`. Для прототипа существенны три
ограничения.

### Прототип открывается офлайн

**Никаких внешних зависимостей**: ни CDN со шрифтами, ни CDN со скриптами,
ни картинок по внешним ссылкам, ни аналитики, ни сети вообще. Проверяется
просто: открыть файл при выключенной сети.

Причина практическая, не эстетическая: прототип открывают на чужом
компьютере, в чужой сети, из архива, через мессенджер. Внешний скрипт, который
не загрузился, превращает демонстрацию в пустой белый экран ровно в тот момент,
когда объясняют заказчику идею.

Практическое следствие: шрифты - только системные, картинки - только inline
или data-URI, иконки - инлайновые, а не шрифтом иконок с CDN.

### Прототип не попадает в продакшен-сборку

Прототип **не является исходником продакшн-кода**. Он лежит в отдельном
каталоге, который исключён из сборки, не импортируется из продакшн-кода, и в
`CHECKLIST.md` есть строка: "прототип не деплоится, в сборку не входит".

Причина: прототип написан без типизации, без тестов и с моками. Если он
попадёт в сборку хотя бы один раз, он там останется навсегда и станет вторым
источником правды о поведении интерфейса.

### Проверяемость того, что показывает прототип

Если в продукте есть AI-слой, прототип должен показывать **состояния AI-ответа**:
придумывает, показывает частичный ответ, ошибка, лимит исчерпан. То же самое
для платежей (ожидание подтверждения, отказ, возврат) - это самые дорогие
места в UX, и на них чаще всего натыкаются уже после кодинга.

Правило проверки: если состояние есть в продукте, но его нет в прототипе,
заказчик не сможет оценить риск до того, как он станет дорогим.

## Готовность этапа

- [ ] Прототип открывается двойным щелчком, без сервера и без сборки.
- [ ] Ни одного фреймворка, ни одной внешней зависимости, ни одного CDN.
- [ ] При **выключенной сети** файл открывается и полностью работает.
- [ ] 2-4 экрана покрывают ядро ценности и основной сценарий пользователя.
- [ ] Визуально соответствует брендбуку: цвета, шрифты, радиусы, отступы, тон.
- [ ] На экране видна явная пометка "прототип, данные искусственные".
- [ ] Работают переходы между экранами.
- [ ] Показаны состояния: пустое, загрузка, ошибка, заполненное.
- [ ] Есть форма с клиентской валидацией.
- [ ] Работает хотя бы один интерактивный элемент, специфичный для продукта.
- [ ] Прототип находится в отдельном каталоге, исключённом из сборки, и не
      импортируется продакшн-кодом; это зафиксировано в `CHECKLIST.md`.
- [ ] Требования к доступности брендбука выдержаны: контраст, фокус, размер
      текста не менее 16 px на мобильном.

Этап закрывается явным подтверждением заказчика.
